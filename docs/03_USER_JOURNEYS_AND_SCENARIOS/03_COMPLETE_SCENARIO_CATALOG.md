## Reading and execution conventions

All scenarios are **PROPOSED** for the new product; none asserts reference-company private behavior. Each row specifies objective (the title and successful outcome), actor/permission, precondition and trigger with required input, state transition/success, alternative and negative flows, and the open policy. The primary actor may act only on the assigned case, branch, user or dealer organization and must hold the stated active role; named supporting actor(s) in the row have their own scoped permission. System actions run under a least-privileged service identity. A dash does not imply broad access. Role IDs are defined in [user roles](../04_ROLES_AND_PANELS/01_USER_ROLES.md); named specialist roles without IDs are **proposed grants pending role-matrix approval**, not implicit permissions.

For every scenario: (1) validate identity, object scope, version and relevant state before a write; (2) store actor or service, case/object ID, UTC time, action, outcome, policy/version and reason/evidence reference in restricted audit records, without raw secrets; (3) emit the fixed analytics event `workflow_outcome_recorded` with scenario_id and completed/blocked/failed outcome after authoritative outcome and purpose checks, excluding identity and sensitive content; (4) where a participant is affected, show a plain-English status such as “Your request is pending review”, “Your changes were saved”, or a specific validation message; do not claim success before confirmation; (5) send an approved transactional notification only to authorized affected recipients when a committed state change warrants one, using delivery status and retry queue separately from business status. A negative decision shows an actionable reason where safe; a provider timeout is **pending/unknown**, not automatically failed. These are design conventions, not evidence that event names, legal notice requirements or integrations have been approved.

Each scenario defines its own expected result in the **Expected success / state** and **Alternative, failure / recovery** columns. Its test reference is `SCN-TST-<ID>`: execute the stated precondition and trigger; assert the stated success, deny unauthorized actors, inject the stated failure, verify audit and analytics once, and check no unrelated case or state changed. This is a proposed test identifier and expected-result definition, not a claim that test scripts exist. Existing foundational links: SCN-01/TST-01/BR-001; SCN-02/TST-02/BR-002; SCN-03/TST-03/BR-003; SCN-04/TST-04/BR-004; SCN-05/TST-05/BR-005. Other rules are described in each row and in the linked rule baseline.

**API/data dependencies:** each action depends on the authoritative domain operation and entities named in its row; canonical endpoint/operation IDs, detailed schemas, user-facing copy variants, event catalog mappings, provider contracts and retention values are **not yet fully assigned or approved**. They must be mapped before implementation; do not invent endpoint identifiers or treat the scenario analytics names as the completed platform-wide event registry. DEC references resolve to the master index. P0 open decisions block production readiness even where a proposed recovery is described.

## Coverage and release limitations

The catalog covers all named seller, auction, buyer and operations topics in the prompt, and additional identity, security, privacy, scheduling, report and financial-recovery scenarios. Some entries are end-to-end variations rather than distinct business capabilities; priority is a proposed review order, not an approved launch commitment. State labels are conceptual and must be reconciled with the formal state and API specifications. Every scenario requires a named business owner, agreed notification text, actual endpoints/entities, lawful basis, acceptance test data, executable/manual test case and sign-off; none is represented as performed. Changes to policies must update affected scenarios and evidence, with P0 decisions resolved before implementation readiness.
